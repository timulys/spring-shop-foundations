# 실행 중인 앱이 요청을 처리할 수 있는지 확인하기

DB가 중단되어도 Spring 앱 프로세스는 계속 실행될 수 있습니다. 이때 주문을 저장하거나 상품을 읽는 요청은 실패합니다. 그래서 컨테이너의 실행 상태와 앱의 요청 처리 준비 상태를 함께 확인합니다.

## 세 종류의 관찰값

| 관찰값 | 확인하는 내용 |
|---|---|
| 컨테이너 Running | 컨테이너의 주 프로세스가 실행 중인지 |
| liveness | 앱 자체가 살아 있는 상태인지 |
| readiness | 현재 앱이 필요한 조건을 갖춰 요청을 처리할 준비가 되었는지 |

이 예제의 readiness 그룹은 `readinessState,db`를 포함합니다. DB 연결에 실패하면 readiness는 503을 반환합니다. liveness에는 DB를 포함하지 않으므로 DB 중단 중에도 앱 자체가 정상이면 200입니다. 이 선택은 DB 의존성이 있는 현재 단일 앱의 실행 구성을 반영합니다. [Spring Boot 상태 그룹](https://docs.spring.io/spring-boot/reference/actuator/endpoints.html)

브라우저에는 상점 기능만 공개하고 상태 API는 컨테이너 내부에서 조회합니다. 내부 상태 응답도 status만 반환하도록 구성했습니다. 구체적인 실패 원인은 앱·DB 로그에서 확인합니다.

## 시작할 때 기다리는 조건

Compose는 DB의 `pg_isready`가 성공해야 앱을 시작합니다. 앱의 readiness 요청이 성공해야 NGINX를 시작합니다. NGINX는 자기 정적 화면 응답을 상태 검사로 사용합니다. `up --wait`는 각 서비스의 상태 검사가 성공할 때까지 기다립니다. [Compose 시작 순서](https://docs.docker.com/compose/how-tos/startup-order/)

앱의 검사는 5초 간격으로 실행하며 한 번의 검사 제한은 4초입니다. 시작 유예 구간 30초 동안의 초기 실패는 실패 횟수에 넣지 않습니다. 그 안에 한 번 성공하면 이후 실패부터 횟수에 넣으며, 연속 3회 실패하면 unhealthy로 표시합니다. curl 요청 자체는 최대 3초를 사용하고, 앱의 DB 연결 대기는 2초로 설정했습니다. 이 값은 해당 실습의 관찰 간격과 대기 제한이며 실제 서비스에서는 부하와 응답 시간에 맞춰 조정합니다. [Docker 상태 검사 규칙](https://docs.docker.com/reference/dockerfile/#healthcheck)

시작 조건은 실행 순서를 정합니다. 실행 후 DB가 중단되면 앱의 상태 검사가 실패하지만 앱 컨테이너가 자동으로 다시 시작되지는 않습니다. 이 Compose 파일은 unhealthy 상태에 따른 자동 재시작 동작을 별도로 구성하지 않았습니다.

## 장애를 나누어 확인하기

| 상황 | 화면·API 결과 | 상태와 복구 |
|---|---|---|
| DB 중단 | 정적 화면 200, DB를 쓰는 API 실패 | 앱 Running, readiness 503, liveness 200. DB 재시작 후 회복 |
| 앱 중단 | 정적 화면 200, API 502 또는 504 | NGINX가 연결할 앱이 없음. 앱을 시작하고 다시 로그인 |
| 앱 DB 비밀번호 오류 | 앱 시작 실패 | 종료 코드와 인증 실패 로그 확인 후 실행 설정 수정 |
| DB 시작 지연 | Compose가 DB 준비를 기다림 | DB가 healthy가 된 뒤 앱과 NGINX 시작 |

NGINX가 파일을 제공하는 경로와 앱이 DB를 조회하는 경로가 다르므로 DB 장애 중에도 정적 화면은 열릴 수 있습니다. 실패한 요청의 상태 코드와 로그를 해당 경로에서 확인하면 문제 위치를 좁힐 수 있습니다.

앱 연결이 거부되면 NGINX는 502를 반환하고, 연결 대기 제한을 넘으면 504를 반환합니다. 이 예제는 연결 대기를 2초, 응답을 읽는 동안의 대기를 8초로 제한합니다. 프록시가 실패 요청을 자동으로 다시 전달하지 않도록 `proxy_next_upstream off`를 지정합니다.

## 복구 뒤 확인할 데이터

DB만 재시작한 경우 앱의 메모리 세션은 유지될 수 있습니다. 앱을 재시작한 경우에는 다시 로그인해야 합니다. 두 경우 모두 같은 DB 볼륨의 이전 주문 번호·상품·금액·상태를 조회해 데이터가 보존되었는지 확인합니다.
