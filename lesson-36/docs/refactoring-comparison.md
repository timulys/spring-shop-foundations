# 같은 구매 시나리오로 비교하기

23강은 `study.shop` 한 패키지에 파일이 모여 있습니다. 24·25강은 상품·장바구니·주문·공통 금액으로 구분했고, 26~28강은 각 기능 안에서 컨트롤러·서비스·도메인·저장소·DTO를 나눴습니다.

| 요구 | 담당 코드 | 바꿀 때 확인할 결과 |
|---|---|---|
| HTTP 요청과 응답 | order.controller / order.dto | 상태 코드와 JSON 필드 |
| 조회·검사·저장 순서 | order.service.OrderService | 미리보기, 저장, 취소, 실패 뒤 상태 |
| 금액과 주문 상태 규칙 | common.money / order.domain | 할인 경계, 배송비, 확정·취소 제한 |
| 상품 조회 계약 | order.service.port.ProductLookup | 같은 코드·이름·단가 또는 빈 결과 |
| DB 상품 변환 | order.infrastructure.DatabaseProductLookup | 엔티티를 스냅샷으로 변환 |
| 주문 영속화 | order.repository | 저장·조회와 트랜잭션 결과 |

## 비교 조건

각 버전을 서로 다른 새 데이터베이스에서 시작합니다. 시드 상품은 P001 키보드 30000원, P002 마우스 15000원, P003 노트 5000원이고 장바구니와 주문은 비어 있습니다. 같은 요청 순서를 사용합니다.

1. 키보드 2개와 마우스 1개를 담습니다.
2. 미리보기에서 상품 합계 75000원, 할인 5000원, 배송비 0원, 최종 70000원을 확인합니다.
3. 미리보기의 cartRevision과 total을 주문 요청에 사용합니다. 201과 Location을 확인합니다.
4. 상품 가격을 99000원으로 바꾸고 저장된 주문을 다시 읽습니다. 주문 항목 단가 30000원과 총액 70000원이 유지되어야 합니다.
5. 주문을 취소합니다. CANCELLED와 원래 항목·금액이 남아야 합니다.
6. 같은 주문을 다시 취소하면 409 ORDER_STATE_CONFLICT입니다.
7. 없는 상품을 담으면 404 PRODUCT_NOT_FOUND, 수량 0이면 400입니다.
8. 상품 단가를 각각 49999원과 50000원으로 놓고 1개를 담습니다. 기본 정책의 총액은 52999원과 45000원입니다.

생성 시각과 오류 응답의 requestId는 실행마다 달라집니다. 생성 시각은 유효한 시각인지와 같은 주문 안에서 보존되는지를 확인하고, requestId는 비어 있지 않은 식별자인지 확인합니다. 두 필드의 값은 버전 간 문자열 동일성 비교에서 제외합니다. 식별자·요청 순서는 같은 초기 상태에서 비교합니다. 브라우저에서도 각각 같은 입력을 넣어 주문과 취소 결과를 확인합니다.

## 추가 정책 과제

`TenPercentDiscountPolicy`는 상품 합계의 10%를 할인하고 원 미만을 버립니다. 75000원의 할인액은 7500원, 최종 금액은 67500원입니다. 49999원은 4999원을 할인하고 배송비 3000원을 더하므로 48000원입니다. 배송비 기준은 할인 전 상품 합계입니다.

이 구현은 기본 앱의 빈으로 등록하지 않습니다. 기본 실행은 `ThresholdFixedDiscountPolicy`를 계속 사용합니다. 새 기능의 의도된 결과와 기존 기능을 보존하는 리팩터링 검사를 구분해 비교합니다.

`subtotal.won() / 10`은 정수 나눗셈으로 원 미만을 버립니다. 양수 범위에서 나눗셈만 하므로 `subtotal * 10 / 100`처럼 중간 곱셈이 long 범위를 넘지 않습니다. 이 경계 검사는 Money의 표현 범위를 검사하며 실제 한 주문의 상품 수 제한과는 별개입니다.
