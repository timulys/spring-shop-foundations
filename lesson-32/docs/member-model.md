# 회원 식별자와 가입 입력

`members.id`는 DB가 생성하는 내부 번호이고, `login_id`는 사용자가 로그인할 때 입력하는 아이디입니다. ` Tim_01 `과 `TIM_01`은 모두 `tim_01`로 정규화합니다. 앞뒤 공백을 제거한 뒤 영문자로 시작하는 3~30자의 영문·숫자·밑줄인지 검사하고, `Locale.ROOT`로 소문자로 바꿉니다. 저장소의 `findByLoginId`에는 정규화한 값을 전달합니다.

`V5__create_members.sql`의 UNIQUE는 같은 로그인 아이디의 두 행을 거부합니다. NOT NULL은 값이 없는 행을 막습니다. CHECK는 저장된 아이디가 정규화된 형식인지 검사합니다. `existsByLoginId`의 조회와 INSERT 사이에는 다른 요청이 저장할 수 있으므로 최종 중복 방지는 DB 유일 제약이 맡습니다.

가입 요청 DTO는 로그인 아이디·표시 이름·입력 비밀번호를 받습니다. 아이디와 이름의 앞뒤 공백은 제거하고, 비밀번호는 입력값을 그대로 유지합니다. 입력 비밀번호는 8~64자로 검사합니다. 31강의 PasswordInputPolicy는 UTF-8 72바이트 제한도 검사하고, SignupService는 검사한 입력으로 해시를 생성합니다.

회원 엔티티는 `password_hash`만 저장합니다. 30강 테스트는 공개된 고정 BCrypt 예제 해시로 회원 제약을 검사합니다. 이 값은 테스트 코드에만 있으며 기본 앱은 회원을 자동 생성하지 않습니다. 형식 검사는 해시 생성의 출처나 보안성을 보증하지 않습니다. 실제 가입에서는 인코더가 계산한 값만 엔티티에 전달합니다.

`MemberResponse`에는 번호·로그인 아이디·표시 이름만 있습니다. DTO의 비밀번호는 JSON 쓰기 전용이며 `toString`에서도 가립니다. 엔티티도 해시를 JSON과 `toString`에서 제외합니다. 비밀번호나 해시를 직접 로그에 출력하지 않습니다.

이 체크포인트에는 가입 API와 화면이 연결되어 있습니다. 현재 32강에는 세션 로그인이 연결되어 있으며, 33강에서 장바구니·주문의 회원별 접근을 연결합니다. 기존 장바구니와 주문을 임의 회원에게 배정하지 않습니다. 이 강의의 별도 실습 DB에서 회원 모델을 검증하고, 실제 회원별 접근은 인증을 연결하는 32~33강에서 다룹니다.
