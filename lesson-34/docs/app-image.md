# 코드가 실행 중인 컨테이너에 도달하는 과정

Dockerfile의 첫 단계는 소스 코드에서 실행 가능한 JAR를 만들고, 둘째 단계는 그 JAR와 Java 실행 환경을 이미지에 담습니다. 최종 이미지에는 빌드용 Gradle과 JDK 컴파일러를 복사하지 않습니다. [Docker 다단계 빌드](https://docs.docker.com/build/building/multi-stage/)

`bootJar`는 애플리케이션 코드와 실행에 필요한 의존성을 담은 Spring Boot JAR를 만듭니다. 이 강의는 JAR 하나를 `java -jar /app/shop.jar`로 실행합니다. 의존성과 앱 코드를 별도 이미지 계층으로 추출하는 최적화는 이 체크포인트의 범위에 포함하지 않습니다. [Spring Boot Dockerfile 설명](https://docs.spring.io/spring-boot/reference/packaging/container-images/dockerfiles.html)

## 주소와 포트

호스트에서 실행하는 앱은 기본 설정의 `127.0.0.1:8080`을 사용합니다. 컨테이너에서는 `SERVER_ADDRESS=0.0.0.0`으로 바꿔 컨테이너 네트워크 인터페이스에서도 요청을 받습니다.

`EXPOSE 8080`은 이미지가 사용할 포트를 나타내는 메타데이터입니다. 호스트 포트를 실제로 연결하는 옵션은 `-p 127.0.0.1:8080:8080`입니다. 앞의 8080은 호스트 포트, 뒤의 8080은 컨테이너 포트입니다. 호스트의 다른 포트를 사용하려면 앞의 값을 바꿉니다.

DB 컨테이너는 Compose 네트워크에서 `db:5432`로 찾습니다. 앱 컨테이너의 `localhost`는 앱 컨테이너 자신을 가리킵니다. 이 단계에서는 DB만 Compose로 만들고 앱 컨테이너를 `docker run`으로 같은 네트워크에 연결합니다. 다음 강의에서 앱·프록시·DB 실행을 Compose 파일로 합칩니다.

## 소스 파일·이미지·컨테이너

이미지를 만든 뒤 호스트의 소스를 수정해도 이미 실행 중인 컨테이너의 파일은 바뀌지 않습니다. 이 실행 명령에는 소스 디렉터리를 연결하는 바인드 마운트가 없습니다. 수정한 소스로 이미지를 다시 빌드하고 그 이미지를 선택해 새 컨테이너를 실행해야 합니다.

`spring-shop:lesson34-v1`에서 `spring-shop`은 이미지 이름이고 `lesson34-v1`은 태그입니다. 태그는 같은 이름으로 다시 빌드하면 다른 이미지 ID를 가리킬 수 있습니다. 서로 다른 버전을 비교하려면 v1·v2처럼 태그를 나누고 실제 이미지 ID도 확인합니다. 기존 컨테이너는 생성 당시 선택한 이미지를 계속 사용합니다.

## 빌드 환경과 실행 환경

빌드 단계에는 Java 21 JDK와 Gradle Wrapper가 있습니다. 실행 단계에는 Java 21 JRE와 완성된 JAR가 있으며 UID 10001의 `shop` 사용자로 앱을 실행합니다. `.dockerignore`는 캐시·IDE 설정·로컬 환경 파일·테스트 소스를 빌드 컨텍스트에서 제외합니다.

이 이미지 빌드는 `bootJar`만 실행합니다. 주문의 DB 저장과 회원별 접근 같은 동작은 별도 테스트 DB에서 검사합니다. 이미지 생성과 실제 서버 요청 성공은 각각 확인할 결과입니다.
