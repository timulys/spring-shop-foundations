# 로그인한 회원의 데이터만 조회하기

회원 A와 B가 같은 상품을 담아도 장바구니는 각각 저장됩니다. 주문에도 회원 번호를 기록하므로 목록·상세·취소에서 로그인한 회원의 주문만 선택할 수 있습니다.

## 회원 번호를 가져오는 곳

컨트롤러의 `@AuthenticationPrincipal ShopPrincipal principal`은 현재 인증 정보의 회원을 받습니다. `principal.memberId()`를 서비스에 전달하고, 서비스는 저장소 조회 조건에 그 번호를 넣습니다. 화면의 JSON이나 쿼리 문자열에는 소유자를 선택하는 필드를 두지 않습니다. 요청자가 임의로 `memberId`를 덧붙여도 현재 세션의 회원 번호를 사용합니다. [Spring MVC 인증 사용자 주입](https://docs.spring.io/spring-security/reference/servlet/integrations/mvc.html)

이 예제에서 인증은 로그인한 회원을 알아내는 과정입니다. 인가는 그 회원이 요청한 장바구니나 주문에 접근할 수 있는지 판단하는 과정입니다. 로그인 성공 뒤에도 모든 주문을 조회하는 쿼리를 사용하면 다른 회원의 주문이 섞일 수 있으므로 조회 조건에 회원 번호가 필요합니다.

## 저장과 조회의 범위

`carts.member_id`에는 회원을 가리키는 외래 키와 유일 제약이 있습니다. 한 회원당 장바구니 하나만 저장할 수 있습니다. 회원가입은 회원 INSERT와 장바구니 INSERT를 한 트랜잭션에서 수행합니다. 장바구니 저장에 실패하면 먼저 저장한 회원도 롤백됩니다.

`orders.member_id`는 주문을 만든 회원입니다. 주문 상세와 취소 조회에는 `memberId`와 `id` 조건을 함께 사용합니다. 현재 회원에게 속하지 않은 주문과 존재하지 않는 주문 모두 `ORDER_NOT_FOUND`·404를 반환합니다. 취소 조회의 쓰기 잠금도 이 조건으로 선택한 주문에 적용합니다.

목록은 행 조회와 전체 개수 조회 모두 회원 조건을 사용합니다. 목록을 읽은 뒤 자바에서 다른 회원의 행을 제거하면 페이지 크기와 전체 개수가 맞지 않을 수 있습니다. 회원 조건을 SQL에 넣으면 해당 회원의 주문 안에서 정렬·페이지 나누기·개수 계산을 수행합니다.

## 로그인과 CSRF가 확인하는 조건

| 요청 | 결과 |
|---|---|
| 비로그인 상품 GET | 200 |
| 비로그인 장바구니·주문 GET | 401 AUTHENTICATION_REQUIRED |
| 인증된 회원의 상태 변경, CSRF 누락 | 403 CSRF_INVALID |
| 인증된 회원, 다른 회원 주문 상세·취소 | 404 ORDER_NOT_FOUND |
| 본인 확정 주문 취소 | 200, CANCELLED |
| 본인 주문 재취소 | 409 ORDER_STATE_CONFLICT |

상태 변경 요청은 CSRF 필터도 통과해야 합니다. 비로그인 POST에 토큰도 없으면 CSRF 필터가 먼저 403을 반환할 수 있습니다. 로그인 여부만 확인하는 테스트에서는 유효한 토큰을 준비해 401을 검사합니다. CSRF 테스트에서는 인증된 세션을 준비한 뒤 토큰만 빼서 403을 검사합니다.

화면은 인증 상태를 확인한 뒤 내 장바구니와 주문 패널을 보여 줍니다. 실제 접근 제한은 서버의 인증 설정과 회원 조건 조회가 담당합니다. 화면을 고치거나 HTTP 요청을 직접 보내도 같은 서버 규칙을 거칩니다.

## 이전 공용 데이터와의 경계

11~32강의 공용 장바구니와 주문에는 회원 번호가 없습니다. V6는 주문 또는 장바구니 항목이 남아 있으면 전환을 중단합니다. 33강은 별도 Compose 프로젝트의 새 볼륨으로 시작하므로 이전 강의 DB를 그대로 보존할 수 있습니다. 실제 서비스의 기존 데이터를 옮길 때는 먼저 소유자 매핑 근거를 마련해야 합니다.
