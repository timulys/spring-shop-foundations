# 원격 상품 조회를 언제 끝낼지 정하기

상품 서비스가 느려지면 새 주문도 상품 값을 기다립니다. 주문 앱은 조회에 쓸 시간을 2.5초로 정하고, 시간이 끝나면 503과 `CATALOG_UNAVAILABLE`을 반환합니다. 상품 정보가 필요한 새 주문은 실패하지만 저장된 주문 상세와 취소는 계속 처리할 수 있습니다.

## 한 번의 제한과 전체 제한

| 설정 | 기본값 | 적용 범위 |
|---|---:|---|
| `CATALOG_CONNECT_TIMEOUT_MS` | 500 | 새 연결 수립 |
| `CATALOG_ATTEMPT_TIMEOUT_MS` | 1500 | HTTP 시도 한 번의 응답 대기 |
| `CATALOG_TOTAL_TIMEOUT_MS` | 2500 | 상품 조회 한 번의 시도·재시도 대기 전체 |
| `CATALOG_RETRY_DELAY_MS` | 100 | 다음 시도 전에 기다리는 시간 |
| `CATALOG_MAX_ATTEMPTS` | 2 | 첫 요청을 포함한 최대 시도 수 |

첫 시도가 1.5초를 사용하면 100ms를 기다린 뒤 남은 약 0.9초를 두 번째 시도에 줍니다. 매번 1.5초를 새로 배정하면 재시도 횟수만큼 전체 대기가 길어지므로, 반복문 밖에서 종료 시각을 한 번 정합니다. 시간의 경과는 시스템 시각 조정의 영향을 피하도록 `System.nanoTime()`으로 계산합니다.

`CatalogCallPolicy`는 양수인 시간 제한과 0 이상의 대기, 1~3회의 시도만 허용합니다. 이 예제의 2.5초는 **상품 HTTP 조회에 배정한 시간**입니다. 로그인 검사·DB 조회·응답 전송까지 합친 브라우저의 전체 시간에는 다른 작업도 들어갑니다. JVM과 운영체제의 스케줄링 때문에 실제 측정에는 작은 초과가 생길 수 있어, 검사에서는 설정 시간과 실제 시간의 차이도 함께 출력합니다.

## 본문이 늦는 경우까지 검사하기

서버는 응답 헤더를 먼저 보내고 본문 전송을 멈출 수도 있습니다. 이 경우에도 클라이언트가 계속 기다리지 않도록 본문 읽기를 제한해야 합니다. 이 프로젝트의 Spring Framework 7.0.10 `JdkClientHttpRequestFactory`는 응답 스트림까지 시간 제한을 적용합니다. `CatalogRetryTest`는 헤더 전 지연과 첫 본문 바이트 뒤의 지연을 따로 주입합니다. [사용 버전의 JDK HTTP 요청 구현](https://github.com/spring-projects/spring-framework/blob/v7.0.10/spring-web/src/main/java/org/springframework/http/client/JdkClientHttpRequest.java)

본문은 최대 1MiB까지만 읽고 JSON을 해석합니다. 빈 본문·잘못된 JSON·예상하지 않은 상품 코드·중복 코드·범위를 벗어난 가격은 `CATALOG_RESPONSE_INVALID`로 처리합니다. 본문 크기 제한은 예상 밖의 큰 응답 때문에 메모리를 계속 사용하는 일을 막습니다.

## 다시 시도할 오류 고르기

| 결과 | 추가 시도 | 주문 API 결과 |
|---|---|---|
| 연결 실패·시간 초과 | 남은 시간과 횟수가 있으면 한 번 | 끝까지 실패하면 503 |
| 원격 502·503·504 | 같은 조건으로 한 번 | 끝까지 실패하면 503 |
| 원격 400·404·500 등 나머지 상태 | 없음 | 503 |
| JSON·상품 응답 규격 오류 | 없음 | 503, `CATALOG_RESPONSE_INVALID` |
| 정상 200 응답에서 요청한 상품 누락 | 없음 | 404, `PRODUCT_NOT_FOUND` |

이 표는 실습의 재시도 정책입니다. 원격 404와 정상 응답의 상품 누락은 다릅니다. 내부 조회 API는 상품이 없을 때 200과 결과 목록을 반환하도록 약속했으므로, 원격 404는 요청 경로나 서비스 구성의 실패로 처리합니다.

내부 묶음 조회는 POST를 사용하지만 데이터를 변경하지 않습니다. 같은 상품 조회를 두 번 수행해도 주문이나 재고를 추가로 만들지 않는 계약에 근거해 재시도합니다. 주문을 만드는 `POST /api/orders`에는 자동 재전송을 추가하지 않습니다. 주문 응답이 끊긴 경우 이미 저장되었을 수 있으므로, 다음 강의에서 같은 요청을 식별하는 영속 키를 먼저 구현합니다. [HTTP 재시도의 멱등성 기준](https://www.rfc-editor.org/rfc/rfc9110.html#section-9.2.2)

## 실패한 주문이 DB를 바꾸지 않는 이유

주문 처리 순서는 장바구니 읽기, 원격 상품 조회, 금액 계산, 로컬 저장입니다. 원격 조회는 주문 DB 쓰기 트랜잭션 밖에서 수행합니다. 상품 조회가 503으로 끝나면 저장 단계에 도달하지 않아 주문 수와 장바구니 수량이 그대로 유지됩니다.

상품 서비스가 복구되어 재시도가 성공하면 상품 값을 한 번 반환받은 뒤 주문 저장을 한 번 진행합니다. 상품 HTTP 호출 두 번과 주문 저장 두 번을 구분해 확인할 수 있습니다. 과거 주문 상세는 저장 당시 상품명·가격·수량을 읽으며, 취소는 기존 주문 상태를 바꿉니다. 두 작업 모두 현재 상품 조회를 호출하지 않습니다.
