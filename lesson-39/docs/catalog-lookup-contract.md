# 내부 상품 묶음 조회 계약

39강의 상품 서비스가 제공하는 계약입니다. 현재 상품 앱에서 이 경로를 호출할 수 있으며, 40강에서 주문 서비스의 HTTP 어댑터를 연결합니다.

## 요청

`POST /internal/products/lookup`에 `Content-Type: application/json`으로 코드 목록을 보냅니다.

```json
{"productCodes":["P001","P002"]}
```

목록은 1~100개이며 각 값은 문자열이어야 합니다. Java의 `String.strip()`으로 앞뒤 공백을 제거한 코드가 비어 있으면 거부합니다. 정리한 코드의 길이는 `String.length()` 기준 1~20이고, 정리한 결과가 중복되어도 거부합니다. 길이는 UTF-16 코드 단위 수입니다. 상품 코드의 대소문자는 구분하며 `P001`은 예제 값입니다. 기존 코드 규칙에 새 문자 패턴 제한을 추가하지 않습니다.

필드 누락·null·빈 목록·101개 이상의 목록·잘못된 코드·중복 코드는 400 `INVALID_PRODUCT_CODES`입니다. JSON 문법 오류나 문자열 목록으로 해석할 수 없는 자료형은 400 `INVALID_REQUEST`입니다. 이 경로는 조회만 수행하고 상품·주문 데이터를 변경하지 않습니다.

## 성공 응답

```json
{"products":[
  {"code":"P001","name":"키보드","unitPrice":30000},
  {"code":"P002","name":"마우스","unitPrice":15000}
]}
```

상태 코드는 200이며 `products`는 배열입니다. 실제로 존재하는 요청 상품만 코드순으로 반환합니다. 요청한 상품이 모두 없으면 빈 배열을 반환합니다. 배열의 각 상품에는 앞뒤 공백이 없는 코드, 비어 있지 않은 상품명, 원 단위 정수 단가가 필요합니다. 상품명 길이는 Java `String.length()` 기준 1~100, 단가는 1~1,000,000원입니다. 요청하지 않은 코드와 중복 코드는 응답에 포함하지 않습니다.

주문 어댑터는 받은 배열의 순서 대신 코드로 상품을 대응시킵니다. 응답에서 요청한 코드가 하나라도 빠졌으면 새 주문 전체를 거부합니다. 존재하지 않는 상품과 통신 실패를 구분하기 위해 다음 기준을 사용합니다.

| 상품 조회 결과 | 주문 API의 응답 |
|---|---|
| 200이며 요청한 상품이 모두 있음 | 단가로 계산 후 주문 처리 계속 |
| 200이며 요청한 상품이 일부 또는 전부 없음 | 404 `PRODUCT_NOT_FOUND` |
| 연결 실패·시간 초과·상품 서버 오류 | 503 `CATALOG_UNAVAILABLE` |
| JSON·필수 필드·자료형·범위 오류, 중복·예상 밖 코드 | 503 `CATALOG_RESPONSE_INVALID` |

주문 API의 오류에는 공통 형식인 `code`, `message`, `requestId`가 들어갑니다. 실패한 응답을 0원 상품으로 바꾸거나 일부 상품만 주문에 넣지 않습니다. 오류가 나면 주문 저장과 장바구니 비우기는 시작하지 않습니다.

## 공개 경로와 배포 변경

최종 구성의 NGINX는 이 내부 경로를 브라우저에 공개하지 않습니다. 주문 앱은 내부 네트워크의 상품 앱 주소로 직접 호출합니다. 이 실습의 컨테이너 네트워크 격리는 네트워크 수준의 접근 범위를 정하며, 서비스 간 인증·암호화는 별도 운영 설계가 필요한 항목입니다.

기존 필드의 의미·자료형·범위를 바꾸는 변경은 양쪽 서비스의 호환성을 검토해야 합니다. 선택 필드를 추가할 때는 주문 어댑터가 기존 필수 필드로 계속 처리할 수 있게 합니다. 이 과정에서는 엔티티 클래스를 공유 라이브러리로 묶지 않고, 각 서비스의 DTO를 계약에 맞춰 정의합니다.
